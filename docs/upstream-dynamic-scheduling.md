# 上游源动态调度实现方案

## 1. 目标

在同一模型配置了多个上游源时，实现严格优先级、高可用故障转移和自动恢复：

- 正常情况下只使用可用的最高优先级上游。
- 当前请求遇到上游故障时，立即尝试下一可用优先级。
- 一个绑定连续失败 3 个独立业务请求后熔断。
- 降级期间每 5 分钟探测更高优先级绑定。
- 更高优先级绑定连续探测成功 3 次，并通过小流量观察后自动回切。

调度状态按“模型 + 上游源 + 上游密钥”绑定维护，避免一个模型或密钥的故障影响整个上游。

## 2. 核心原则

1. `priority` 数值越小，优先级越高。
2. 不同优先级之间不做权重分流。
3. 只有相同优先级的健康绑定才按 `routing_weight` 分流。
4. 请求级故障转移和全局熔断分开：单次故障立即保护当前请求，连续 3 次故障才改变绑定的全局状态。
5. 探测请求独立于用户请求，不复制用户业务数据，也不将探测响应返回给用户。
6. 流式响应发送首包后不得切换上游。

## 3. 请求调度流程

```text
请求进入
   |
   v
选择健康的最高优先级组
   |
   v
组内按权重选择第一个目标
   |
   +-- 成功 ----------------------> 返回响应，清零该绑定连续失败数
   |
   +-- 可切换错误 --> 尝试下一目标 --> 直到成功或候选耗尽
```

单次请求中，每个候选绑定最多调用一次。候选顺序为：

1. 当前最高可用优先级组内按权重选择。
2. 同组剩余绑定按调度顺序排列。
3. 再按优先级从高到低追加后续可用组。

`MaxRetries` 表示一次请求允许尝试的上游目标总数，且不能超过候选数量。

## 4. 错误分类

| 错误类型 | 当前请求切换 | 计入连续失败 | 状态处理 |
| --- | --- | --- | --- |
| 连接失败、连接超时、首包超时 | 是 | 是 | 达到阈值后熔断 |
| HTTP 429 | 是 | 是 | 优先遵循 `Retry-After`，否则使用默认冷却 |
| HTTP 5xx | 是 | 是 | 达到阈值后熔断 |
| 已确认的上游凭证 401/403 | 是 | 不走三次阈值 | 立即熔断对应密钥绑定 |
| 参数错误、模型不支持等业务 4xx | 否 | 否 | 原样返回 |
| 客户端主动取消 | 否 | 否 | 返回 499，不更新上游健康状态 |
| 流式响应首包后的中断 | 否 | 按上游故障记录 | 不重放请求 |

连续失败按独立业务请求计算。任意一次业务成功会把该绑定的连续失败数清零。

## 5. 状态机

```text
                     连续失败达到 3 次
             +--------------------------------+
             |                                v
          CLOSED                            OPEN
             ^                                |
             |                                | 到达 next_probe_at
             |                                v
             |                            HALF_OPEN
             |                                |
             |                         首次探测成功
             |                                v
             |                           RECOVERING
             |                                |
             |                      连续探测成功共 3 次
             |                                v
             +--------------------------- OBSERVING
                         观察期通过

HALF_OPEN / RECOVERING / OBSERVING 任意探测或观察失败：回到 OPEN。
```

状态说明：

| 状态 | 业务流量 | 行为 |
| --- | --- | --- |
| `closed` | 正常流量 | 参与严格优先级调度 |
| `open` | 无 | 等待下一次恢复探测 |
| `half_open` | 无 | 正在执行首次恢复探测 |
| `recovering` | 无 | 以固定间隔完成后续恢复探测 |
| `observing` | 少量 | 通过受控真实流量确认恢复稳定性 |

## 6. 降级与恢复

### 6.1 降级

- 当前最高优先级绑定熔断后，从剩余健康绑定中选择优先级最高者。
- 当前使用的低优先级绑定发生故障时，执行同样的请求级切换和连续失败规则。
- 每次选择都重新评估候选状态，因此已恢复的更高优先级绑定可以重新成为主源。

### 6.2 后台探测

- `open` 绑定到达探测时间后进入 `half_open`。
- 第一次探测成功后进入 `recovering`，之后每隔 10 秒继续探测。
- 连续成功达到 3 次后进入 `observing`。
- 任一次探测失败都会清零恢复成功次数，回到 `open`，并在 5 分钟后重试。
- 多个更高优先级绑定同时恢复时，最终使用其中优先级最高的健康绑定。

探测必须调用能够覆盖真实模型链路的最小请求，并设置独立超时。若上游提供的健康接口无法验证鉴权、模型和推理链路，则不能仅依赖健康接口。

### 6.3 小流量观察

- 观察期默认 30 秒。
- 观察期仅接收同优先级正常权重的 10% 流量，最小有效权重为 1。
- 观察期内成功请求正常累计；到期且无失败后转为 `closed`。
- 观察期内出现可切换错误，立即回到 `open`。

## 7. 并发和持久化

- 调度状态保存在 `model_route_bindings`，不能只保存在进程内存。
- 状态转换使用带当前状态条件的原子更新，防止并发请求重复转换。
- 多实例部署时，探测任务通过数据库租约抢占，同一绑定同一时刻只允许一个实例探测。
- 进程内平滑加权状态只用于同优先级选择，不作为健康状态的事实来源。
- 管理员手动恢复绑定时，清空失败次数、恢复成功次数、冷却时间和探测租约。

## 8. 默认参数

| 参数 | 默认值 |
| --- | ---: |
| 连续失败阈值 | 3 次 |
| 恢复探测周期 | 5 分钟 |
| 恢复确认次数 | 3 次 |
| 恢复确认间隔 | 10 秒 |
| 探测超时 | 10 秒 |
| 观察期 | 30 秒 |
| 观察流量比例 | 10% |

以上参数作为服务端默认值，第一阶段不开放普通用户修改。

## 9. 可观测性

每次用户请求尝试和后台探测至少记录：

- 请求或探测 ID。
- 模型绑定、上游源和密钥 ID。
- 调用开始、结束和耗时。
- HTTP 状态码或网络错误分类。
- 调用前后调度状态。
- 连续失败次数或恢复成功次数。
- 是否发生熔断、降级或回切。

不得记录上游密钥、用户提示词或完整敏感响应。

## 10. 验收标准

1. 最高优先级健康时，业务请求不会被分配到低优先级源。
2. 最高优先级单次返回 5xx 时，本次请求能由下一优先级源成功完成。
3. 前两次独立失败不会全局熔断，第三次连续失败后进入 `open`。
4. 任意成功请求会清零连续失败计数。
5. `open` 绑定不会承接业务流量。
6. 降级期间按 5 分钟周期恢复探测，任一次探测失败会重新计时。
7. 连续 3 次探测成功后进入观察期，观察成功后恢复正常流量。
8. 多个源恢复时，始终选择健康源中优先级最高者。
9. 相同优先级绑定按权重分流，不同优先级之间不分流。
10. 客户端取消和非重试业务 4xx 不改变绑定健康状态。
11. 流式首包后失败不会向其他上游重放。
12. 多实例并发探测同一绑定时，只有一个实例获得执行权。

## 11. 实施顺序

1. 修正候选排序，落实严格优先级和同级权重。
2. 将熔断阈值统一为连续 3 次，并补充错误分类。
3. 完善恢复状态和持久化字段。
4. 增加后台探测循环和多实例探测租约。
5. 增加观察期流量控制。
6. 补充状态机、路由、并发和端到端测试。
